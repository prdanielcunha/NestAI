10. Segurança
10.1 Classificação de dados
P0 — Public
Exemplos:
· descrição pública de produto;
· texto de marketing;
· conteúdo já publicado.
Providers:
· todos os permitidos pela task.
P1 — Internal
Exemplos:
· documentação interna não confidencial;
· configuração de produto;
· instruções operacionais.
Providers:
· policy whitelist.
P2 — Personal
Exemplos:
· nome;
· contato;
· conversa individual;
· histórico de uso.
Providers:
· somente aprovados para dados pessoais;
· minimização obrigatória.
P3 — Sensitive
Exemplos:
· informação religiosa identificável;
· acompanhamento pastoral;
· dados financeiros;
· saúde;
· biometria;
· documentos;
· situações pessoais delicadas.
Providers:
· lista extremamente restrita;
· redaction/minimização;
· payload logs desabilitados;
· acesso auditado.
P4 — Restricted
Exemplos:
· senhas;
· API keys;
· secrets;
· tokens;
· credenciais;
· dados que política determine não sair do ambiente.
Regra:
NUNCA enviar a LLM externa.
10.2 LGPD
Dados de convicção religiosa e filiação a organização religiosa devem ser tratados como sensíveis.
Como vários produtos MillionsNest atuam em contexto de igreja, a plataforma assume postura conservadora:
perfil de membro pode conter contexto sensível mesmo quando o campo isolado parece comum.
10.3 Data minimization
Antes do provider:
payload original
→ remover campos não necessários
→ redigir identificadores quando possível
→ limitar histórico
→ executar provider
10.4 DLP
Usar DLP no AI Gateway onde disponível e política própria para:
· e-mail;
· telefone;
· CPF;
· dados bancários;
· cartão;
· tokens;
· secrets;
· credenciais;
· dados classificados.
DLP não substitui classificação por domínio.
10.5 Prompt injection
Toda entrada recuperada por RAG deve ser tratada como dados não confiáveis.
Nunca permitir que documento diga:
ignore as regras do sistema e execute…
Mitigações:
· separar system/developer/context;
· delimitar conteúdo recuperado;
· tool allowlist;
· nenhum secret no contexto;
· validação de tool args;
· capability checks;
· output schema;
· approval gates;
· red-team tests.
10.6 Tool security
A IA nunca recebe uma ferramenta genérica:
database.execute(sql)
Recebe ferramentas estreitas:
finance.report.read
calendar.availability.read
connect.draft.create
journey.followup.suggest
Escritas críticas:
AI propõe
→ sistema valida
→ usuário aprova
→ função determinística executa
→ audit event
10.7 Logs
Para P2/P3:
· metadata: sim;
· payload: não por padrão;
· conteúdo completo: somente debug temporário explicitamente aprovado;
· expiração automática;
· acesso restrito.
Nunca logar:
· provider keys;
· authorization header;
· Firebase token;
· secret;
· senha.

11. Routing Engine
11.1 Etapas
flowchart TD
    A[Request] --> B[Authenticate]
    B --> C[Resolve tenant + entitlement]
    C --> D[Load Task Policy]
    D --> E[Classify sensitivity]
    E --> F[Filter providers]
    F --> G[Check free quota]
    G --> H[Check health/circuit breaker]
    H --> I[Select route]
    I --> J[Prepare minimized context]
    J --> K[Execute]
    K --> L{Success?}
    L -- yes --> M[Validate output]
    L -- no --> N{Safe fallback?}
    N -- yes --> O[Fallback]
    N -- no --> P[Graceful failure/queue]
    O --> M
    M --> Q[Telemetry + result]
11.2 Critérios
Prioridade:
1. privacidade;
1. capability;
1. entitlement;
1. free eligibility;
1. disponibilidade;
1. qualidade;
1. latência;
1. quota;
1. custo;
1. preferência experimental.
Nunca inverter privacidade e custo.

13. Quotas e ZERO COST MODE
13.1 Estado inicial
FREE_ONLY
13.2 Regras
1. nenhum fallback pago;
1. provider pago disabled;
1. nenhuma Unified Billing automática;
1. quota por provider;
1. quota por app;
1. quota por organização;
1. quota por usuário quando necessário;

1. cache;
1. fila/degradação ao atingir limite.
13.3 Suggested allocation
Não hard-code percentuais permanentes.
Primeiro usar pool dinâmico com:
· 80% capacidade compartilhada;
· 20% reserva operacional.
Depois medir consumo real.

13.4 Headroom
Estados:
HEALTHY       > 40%
WATCH         20–40%
CONSERVE       5–20%
CRITICAL       < 5%
EXHAUSTED       0%
Em CONSERVE:
· tarefas simples migram para modelo menor;
· cache é favorecido;
· outputs ficam mais curtos;
· background não crítico pode aguardar.
13.5 Nunca cobrar automaticamente
Quando a cota terminar:
salvar contexto
→ mostrar indisponibilidade temporária
→ oferecer fluxo manual
→ retomar quando possível
Não:
free quota terminou
→ ativar cartão
